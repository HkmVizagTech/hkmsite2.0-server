## What to make identical
1. **lean vs hydrated reads.** The old code returns Mongoose documents (defaults filled in for fields missing in old documents) except where it called `.lean()` (raw document, nothing filled). The repos now do exactly this: `find/findOne/findById/insert/updateOne/updateById/deleteById` hydrate by default and return the raw shape with `{ lean: true }`; `repo.fromRow(row, { lean: true })` for raw SQL rows. Go through **every `.lean()` and every non-lean query** in your old files and make the new call match (also `.select()` projections, `.populate()`, `.sort()`, `.skip()/.limit()`, `.distinct()`, `.countDocuments()`, `.exec()`). Legacy documents (missing newer fields) in the test data exercise this; the shape tests will show `missing in A (B=false)` style diffs when you get it wrong.
2. **Malformed / non-ObjectId ids and values.** Mongoose throws `CastError` (message `Cast to ObjectId failed for value "abc" (type string) at path "_id" for model "event"`) when an id is cast: `findById(x)`, `findByIdAndUpdate/Delete(x)`, `find({ _id: x })`, and filters on any ObjectId-typed path (`eventId`, `donorRecordId`, `festivalId`, `createdBy`, refs...). The controller's catch block then decides the response (status/body vary per controller: sometimes `{ message: "Server error" }`, sometimes with `error: err.message`). Reproduce exactly, using `castId(value, "<registeredModelName>", "<path>")` from `src/db/pg.js` (the model name is the string passed to `mongoose.model(...)` in the old model file) at the same points where Mongoose would cast. Number/Date/Boolean/ObjectId casting of body values (e.g. `"12"` -> 12, `"abc"` -> `Cast to Number failed for value "abc" (type string) at path "amount"`) and `required`/`enum`/`min`/`max`/`maxlength`/`match` validators must produce the same status and message on `create/save`; remember Mongoose runs validators on `save()`/`create()` but **not** on `findByIdAndUpdate` unless `runValidators` is set (check the old code!). Setters: `trim`, `lowercase`, `uppercase` on the schema must be applied on writes exactly where Mongoose applied them (including on `findByIdAndUpdate` casting) so stored values are identical.
3. **Strict mode**: unknown body fields are silently dropped by Mongoose; the repo already ignores unknown columns on writes and treats unknown filter fields as "matches nothing".
4. **Ordering / pagination / limits**: same default order (a query without `sort` returns insertion order = `_id` order: add `ORDER BY id` when the old code had no sort), same page/limit clamping, same behavior for page=0, negative, NaN, huge, repeated params (`?a=1&a=2` becomes an array in Express), non-string query values, etc.
5. **Responses byte for byte**: status codes, JSON shapes and field names, error messages, CSV/text bodies (exact bytes), headers that matter (`content-type`, `content-disposition`), number formatting/rounding, date serialization.
6. **Side effects**: every write the old code performed (including side tables, caches, invalidations, notifications) and nothing more; the resulting database state must match for the same request sequence.
